第一课：换了保存方式，为什么菜单也要改？

你已经写过两个版本：一个把任务写进 JSON，一个把任务写进 MySQL。用户做的操作没有变：选“添加任务”，输入内容，按回车。但程序里面，负责保存任务的代码变了。

先看菜单真正需要什么

String content = sc.nextLine();
dao.insert(content, date);

菜单需要把内容和日期交出去。它不需要知道 SQL 怎么写，也不需要知道 JSON 文件放在哪里。你已经用 TaskDao 分担了数据库操作，这一步让菜单短了很多。

现在假设你想保留两种保存方式：有时用文件，有时用数据库。问题来了：菜单里写着 TaskDao，怎样换成文件保存？

先停一下，想一想

如果每个菜单分支都写一次“用文件还是用数据库”的判断，以后增加一种保存方式时，需要改几个地方？

想好后，再看解释

凡是涉及保存、读取和删除的分支，都可能需要检查。我们可以先把菜单要调用的方法统一起来，让选择集中到创建对象的位置。

先给两种保存方式约定一个共同动作

为了看清这个变化，我们先只讨论保存，并暂时只传任务内容。约定很简单：负责保存的类，都要有一个 save 方法，接收一段文字。Java 可以把这条约定写下来：

interface TaskStore {
    void save(String content);
}

把这一小段从头读一遍：interface 表示我们正在写一个接口；TaskStore 是它的名字；save 表示约定的动作；String content 表示这个动作要接收文字；void 表示它没有返回值。这里没有花括号里的操作，因为真正的保存工作要交给具体的类。

接口现在只回答一件事：“别人怎样调用我？”接下来需要一个类回答：“我收到调用后做什么？”

class ScreenStore implements TaskStore {
    public void save(String content) {
        System.out.println("收到任务：" + content);
    }
}

先用终端输出代替真实保存，便于观察。implements TaskStore 表示这个类接受刚才的约定；因此它提供同名、同参数的方法。方法写成 public，其他代码才能通过接口调用它。

菜单现在可以怎样写？

TaskStore store = new ScreenStore();
store.save("学习 Java");

第一行的左边说：“我打算通过 TaskStore 约定来使用这个对象。”右边创建 ScreenStore，它提供具体做法。第二行通过约定调用 save，最后输出“收到任务：学习 Java”。

先停一下，想一想

如果右边换成另一个实现 TaskStore 的类，第二行 store.save(...) 还需要改吗？

想好后，再看解释

不需要改调用方式。Java 会执行实际对象提供的 save。若这个类把任务写入文件，调用就会进入文件保存代码；若它写入数据库，就会进入数据库代码。

这就是多态在这里的用途

同一个 store.save 调用，可以由不同对象执行各自的做法。这种行为叫多态。你先抓住它在项目里的意义：菜单按同一份约定调用，具体保存方式在创建对象时选择。

接口不能替你自动搬运数据。原来的 JSON 读写、SQL 和数据库连接仍要放进相应实现中。我们只是整理了调用关系。

用什么判断自己懂了？

试着说明这两行中的每一部分：TaskStore 是约定，store 是变量，ScreenStore 是具体类，new 创建对象，save 是通过对象调用的方法。如果你能解释“换右边的对象，为什么左边的调用还能成立”，这一课的主要内容就清楚了。

需要运行验证时，打开接口的完整程序。它会用两个不同对象接收同一句话。先猜输出，再运行。

第二课：两种保存方式都要检查空任务，怎么办？

接着刚才的问题。现在你不允许保存空任务。文件保存要检查一次，数据库保存也要检查一次。规则相同，写两遍后，如果规则改变，两边都要改。

先停一下，想一想

可以把检查单独提成一个方法吗？

想好后，再看解释

可以。共用方法是一种选择。若几个相关类还需要共用一套执行步骤，也可以把步骤放进一个父类。下面学习的抽象类适合这种情况。

把共同步骤写在父类中

abstract class CheckedStore {
    public final void save(String content) {
        if (content == null || content.isBlank()) {
            throw new IllegalArgumentException("任务内容不能为空");
        }
        write(content);
    }

    protected abstract void write(String content);
}

先从 save 看：收到内容，检查是否为空，检查通过才调用 write。这里已经给出了完整的顺序。但父类还不知道数据写到哪里，所以把 write 留空，并加上 abstract。子类需要填上这一步。

class ScreenStore extends CheckedStore {
    @Override
    protected void write(String content) {
        System.out.println("保存：" + content);
    }
}

extends 表示继承。ScreenStore 沿用父类的 save，再提供自己的 write。调用 new ScreenStore().save("喝水") 时，会先执行父类检查，再进入子类的 write。输出是“保存：喝水”。

先停一下，想一想

如果传入的是三个空格，write 还会执行吗？

想好后，再看解释

不会。isBlank 判断空白内容，检查处会抛出异常，程序离开这次保存过程。

为什么有 public、protected 和 final？

save 是给外面调用的入口，所以写 public。write 留给相关子类实现，所以用 protected。final 表示子类不能重写 save，检查顺序由父类统一保留。private 用于类的内部成员；不写访问修饰符时，同包代码可以访问。protected 也允许同包访问，跨包子类访问时还需要符合继承规则。

接口用来约定调用方式；抽象类还能集中保存共同状态和实现。选择时先看你是否真的有共用步骤。Java 类只能直接继承一个类，但可以实现多个接口。

运行与对照：抽象类完整程序。可以先预测空内容时会在哪一行停止。

第三课：任务应该装在哪里？

你已经把多条任务放进 List。假如列表里还能混进整数或数据库连接，取出来时就很难知道该怎样处理。我们希望添加时就发现放错了东西。

List<String> tasks = new ArrayList<>();
tasks.add("喝水");

List 告诉编译器，这个列表装字符串。若写 tasks.add(3)，编译器会报告类型不匹配。尖括号里的类型约束就是你已经在使用的泛型。

如果自己写一个容器呢？

class Box<T> {
    private T value;
    public void put(T value) { this.value = value; }
    public T get() { return value; }
}

T 是给类型留的位置。创建 Box 后，put 接收字符串，get 返回字符串。创建 Box 后，它们对应整数对象。我们用一份代码描述盒子的动作，再让使用者指定装什么。

先停一下，想一想

Box 的 get() 返回什么类型？需要先判断它是不是字符串吗？

想好后，再看解释

返回 String。泛型已经告诉编译器类型，通常无需再转换或判断。泛型类型参数要使用引用类型，例如 Integer，不能使用 int。

换一种需求，就可能换一种集合

待办列表需要按顺序显示，可以用 ArrayList。同一个标签只想保留一次，可以用 HashSet。输入任务编号就想取出对应任务，可以用 HashMap。先问“是否允许重复、是否需要顺序、是不是按键查找”，再选集合。

HashSet 和 HashMap 不保证插入顺序。要保留插入顺序，可以看 LinkedHashSet 和 LinkedHashMap；要按键排序，可以看 TreeMap。先把前三种用熟，再按需求增加选择。

运行与对照：泛型盒子完整程序。尝试往 Box 放一个整数，看看编译器指出哪一行。

第四课：按编号找任务，HashMap 怎么认出这个编号？

假设你输入编号 3，想拿到“喝水”。用列表时，可以逐项比较编号。Map 则把“编号与任务”保存成对应关系：

tasks.put(3, "喝水");
String content = tasks.get(3);

这里 tasks 是 Map。第一次用 put 建立对应关系，随后 get 根据键查找。如果再次 put(3, "休息")，编号 3 对应的值会被替换。

先定位，再核对

HashMap 利用键的 hashCode 计算可能存放的位置，再用 equals 核对是不是要找的键。不同键可能落在同一位置，这叫哈希冲突。冲突时还需要进一步查找，不能只凭哈希值认定相等。

先停一下，想一想

如果两个键的 hashCode 相同，它们一定是同一个键吗？

想好后，再看解释

不一定。还要看 equals 的判断。相等的键必须有相同哈希值，反过来不能成立。

什么时候需要自己写 equals？

整数和字符串已经提供了合适的比较方式。如果你创建了自己的 TaskKey 类，又希望“编号相同就算同一个键”，就要在这个类里写清 equals，并让 hashCode 使用同样的编号。键存入 Map 后，参与比较的数据应保持稳定，否则可能难以再次找到它。

运行自定义键的完整程序。它创建两个不同的 TaskKey 对象，只要编号都是 3，仍能查到同一项。看懂这个现象后，再读 equals 的每一个判断。

HashMap 内部会组织同一位置的多个条目，常见实现会使用链表，并在满足条件时转换成树。你现在先掌握“定位位置、判断相等、处理冲突”，后面读源码就有了入口。

第五课：数据库查询失败，该由谁告诉用户？

用户选择查看任务，数据库却没有启动。Dbutil 无法返回连接，TaskDao 就无法查询。这时失败信息需要传回调用路径，让某一层处理。

Todo → TaskDao → Dbutil
                连接失败
Todo ← TaskDao ← SQLException

throw 是实际抛出异常的动作。throws 写在方法声明上，表示异常可能交给调用者。try 包住可能失败的操作，catch 接住相应类型的异常。

先停一下，想一想

如果 TaskDao 接住异常、打印报错，然后返回空列表，菜单能区分“没有任务”和“查询失败”吗？

想好后，再看解释

仅凭这个空列表无法区分。可以让查询异常继续传给菜单，由菜单显示“查询失败”；正常返回空列表时，再显示“暂无任务”。

先看一个容易观察的失败

try {
    int number = Integer.parseInt("你好");
    System.out.println(number);
} catch (NumberFormatException e) {
    System.out.println("请输入数字。");
}

这是方法内片段。文字“你好”无法转换成整数，程序跳到匹配的 catch，所以打印“请输入数字”。改成“3”就会转换成功，打印 3。异常发生后，try 中没有执行的语句会被跳过。

SQLException 和 IOException 属于受检异常，通常要求捕获处理，或通过 throws 声明传递。NumberFormatException 属于 RuntimeException，不强制声明。它们都在 Exception 体系中；Error 则通常涉及运行环境或系统层面的严重问题。

运行与对照：异常传递完整程序。跟着调用顺序找出谁失败、谁处理。

第六课：只挑出学习任务，再加一段提示

假设有“学习 Java、喝水、学习 Git”三条任务。你想只显示学习任务，并在每条前面加上“待办：”。先用普通话列出步骤：取出任务，筛选，再转换文字，最后收集结果。

List<String> result = tasks.stream()
        .filter(t -> t.contains("学习"))
        .map(t -> "待办：" + t)
        .toList();

这是方法内部的片段，tasks 是已有的字符串列表。stream 开始这轮处理；filter 只保留判断为真的项；map 把留下的项变成新文字；toList 把结果交回列表。

先停一下，想一想

“喝水”会进入 map 吗？原来的 tasks 会因为这段筛选而少一项吗？

想好后，再看解释

“喝水”未通过 filter，所以不进入后面的 map。原列表仍保留三条内容，result 保存这次处理的结果。

箭头里到底写了什么？

t -> t.contains("学习") 表示“接收一项 t，返回它是否包含学习”。Java 用函数式接口描述这种只有一个抽象方法的动作，Lambda 提供动作的实现。filter 需要一个返回真假值的判断；map 需要一个返回新值的转换。

这类中间步骤通常等到终止操作才实际处理。这里 toList 是终止操作。一次 Stream 使用完，再做另一轮处理时需要重新创建。

找不到一条任务时，返回什么？

findFirst 可能找到第一条，也可能一条都找不到，因此返回 Optional。你可以用 orElse("没有找到") 提供空结果时的文字；用 ifPresent 只在有值时执行动作；用 orElseThrow 在缺少结果时抛出异常。

第七课：写了中文，文件里保存的是什么？

回想 JSON 保存。Gson 把任务变成一段文字，但硬盘保存的是字节。写入器要按编码规则把文字变成字节，读取时再按同一规则还原。UTF-8 就是这样的规则。

任务对象 → Gson → JSON 文字 → UTF-8 编码 → 文件字节
文件字节 → UTF-8 解码 → JSON 文字 → Gson → 任务对象

所以“转换 JSON”和“写文件”各做一步。Gson 负责数据格式转换；Writer 或 Files 负责把文字交给文件系统。编码不一致时，读回的中文可能出现乱码。

为什么有字节流和字符流？

图片和压缩包需要保留原始字节，可以使用 InputStream、OutputStream。处理文本时，Reader、Writer 按字符工作。InputStreamReader 把字节按指定编码转成字符；OutputStreamWriter 负责相反的方向。

你看到的 BufferedReader 又多做了一件事：暂存一批读取的数据，减少频繁访问底层数据源的次数，并提供 readLine 逐行读取。Files.newBufferedReader 可以帮你创建这样的读取器。

先停一下，想一想

readLine 返回 null 时，是读到一行写着“null”的文字，还是已经没有下一行？

想好后，再看解释

表示文件已经读完。如果文件里真写了一行 null，返回的是字符串“null”，与空引用 null 不同。

小文件可以用 Files.readString 一次读取。大文本如果可以逐行处理，就可以用 BufferedReader，减少同时放在内存里的内容。文件、读取器和数据库连接用完要关闭，try-with-resources 可以自动完成关闭。

运行临时文件完整程序。它写入两行中文，再逐行读回，还会读取字节数量。文件操作结束后会删除这个练习临时文件。

第八课：代码上的标记，程序怎样读到？

假设你写了很多负责保存的类，希望一个工具自动显示每个类的说明。你可以给类加一段文字标记，再让工具去读。标记可以用注解表示，运行时查看类的信息可以用反射完成。

@Description("负责保存任务")
class DemoStore {
}

这里的 Description 是练习中自己定义的注解。它把说明附在 DemoStore 类上。你还需要写代码读取它，才能把说明显示出来。

Class<DemoStore> type = DemoStore.class;
Description info = type.getAnnotation(Description.class);
if (info != null) {
    System.out.println(info.value());
}

先取得描述 DemoStore 的 Class 对象，再查这个类上有没有 Description。找到了，就通过 value 取出说明。没找到时，info 是 null，因此需要先判断。

先停一下，想一想

如果删掉类上面的 @Description，输出会怎样变化？

想好后，再看解释

程序找不到标记，info 是 null，这段代码就不打印说明。

自定义注解需要说明什么？

用 @interface 定义注解，用 RetentionPolicy.RUNTIME 指定保留到运行时，用 Target 指定可以放在什么位置。TYPE 表示可以放在类等类型声明上。完整例子会把这几处放在一起，你可以先运行，再逐行对照。

框架也会制定类似的约定：用户在类上写标记，框架读取标记，再按规则创建对象或调用方法。反射还能查看构造方法、字段和方法。你见过的 @Override 则由编译器检查，用来确认方法确实重写或实现了已有方法。
