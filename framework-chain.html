每条请求都要做的事，放在哪里？

每个接口都写日志、查身份、处理跨域，很快就会写出许多相似代码。

你可以把一次请求经过的路想成办事窗口前的通道。先记下到达时间，核验必要凭证，然后交给具体窗口。窗口处理完，还要记录结果和耗时。各个窗口办不同业务，共同流程却可以只安排一次。

在 Spring MVC 中，Servlet Filter 可以围绕请求处理。拦截器也能在控制器执行前后参与，并更接近 MVC 的处理方法信息。它们都可以承担部分公共工作，使用位置要结合执行范围选择。

先让同一条请求留下一个编号

你点添加后出了错，服务器上可能同时有很多人的请求。只写“保存失败”，很难知道对应谁的哪次操作。这一篇要写的 RequestLogFilter 给每条请求生成 requestId，放进响应头 X-Request-ID，也放进错误响应。

日志中带同一个编号，排查时就能把接收、处理和失败几段信息连起来。这里的 requestId 标识一次应用请求；如果跨多个服务传播，需要进一步接入分布式 traceId，而不能只靠每个服务各生成一段编号。

请求向里走，响应再往外回来

过滤器的主要结构是：

try {
    chain.doFilter(request, response);
} finally {
    // 记录耗时，并清理本次请求放入的日志上下文
}

chain.doFilter 把请求交给后面的处理环节。调用之前做的事先发生；后面的环节结束，程序再回到这里执行 finally。多个过滤器形成链，先进入的外层通常最后收尾。如果不继续调用链，可以提前结束请求，例如返回拒绝访问。

示例用 request.setAttribute 保存 requestId，下游通过同一个 request 取出。这是一次请求范围内传值。日志的 MDC 则让当前线程的日志带上编号；线程会复用，所以 finally 必须清理，避免下一次请求带上上一个人的编号。进入异步线程后，不能假定这些线程上下文自动传过去。

登录检查与任务权限各守一段

所有“我的任务”都需要先确认用户身份，适合集中放在认证链中。认出用户以后，service 仍要确认任务是否属于这个用户。只验证登录，无法阻止小明修改别人的任务编号。

正式登录应使用 Spring Security 等成熟组件，把认证、访问控制与会话策略接好。目前这份练习还没有实现登录，接入多人使用前需要补齐身份与任务归属检查。

跨域也可以集中配置允许的网页来源、方法和头部。带 Cookie 时需要具体来源与凭证规则，先前 HTTP 教程中的要求仍然适用。使用 Spring Security 时，要与安全链的 CORS 配置协作，让 OPTIONS 预检得到合适处理，避免先被登录规则一概拦住。

若页面运行在另一个端口

为了把前面 HTTP 教程中的跨域规则接到框架里，可以新增 WebConfig.java。下面是完整配置类，放在 com.example.todo 包中；导入依赖已包含在 Web MVC starter 里：

package com.example.todo;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.CorsRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("http://127.0.0.1:8080")
                .allowedMethods("GET", "POST", "PATCH", "DELETE", "OPTIONS")
                .allowedHeaders("Content-Type");
    }
}

这份配置允许 8080 的网页读取 /api/ 下的接口。后端端口仍是 8090，所以来自其他来源的网页不在这份许可中。等接入 Cookie 登录时，再明确配置凭证与安全链；这份配置没有启用跨源凭证。它属于可选扩展，前面的接口可以先直接用 curl 访问。

请求太多时，怎样让服务喘口气

如果有人每秒点击几百次，后端和数据库可能忙不过来。限流可以为某个身份、接口或来源限制一段时间内的请求量。超过时返回 429，必要时带 Retry-After，告诉客户端稍后再试。

一个小项目可以先理解令牌桶的直觉：桶中有限额，来一次请求用掉一个，额度按一定速度补回；桶空就暂时拒绝。按 IP 限制可能把同一网络的多人算在一起，按用户限制则依赖可靠身份。多个应用实例还需要共同计数或分布式限流方案，不能认为每个进程单独计数就是全站限额。

限流组件可以放在网关或应用过滤链中，但应由经过验证的组件承担并发计数与时间处理。把规则写清楚，比为了加一个过滤器就随意设置阈值更重要。

这些步骤为什么要有顺序

先取得请求编号，后面的错误日志才好追踪；先识别用户，才便于按用户限流；需要放行的预检应在合适位置处理。不同规则的次序会改变结果，因此新增公共环节时，要同时想它应当围住谁、又会被谁围住。

这条链承担共同责任，Controller 继续关心任务请求。这样修改一次日志规则，不必翻遍每个任务方法。

亲手把请求编号接进来

在 com.example.todo 包中创建 RequestLogFilter.java。文件顶部的 servlet 类型来自 Web 依赖，Logger 和 MDC 来自框架提供的日志组件；UUID 是 Java 自带工具。

package com.example.todo;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import java.io.IOException;
import java.util.UUID;
@Component
public class RequestLogFilter extends OncePerRequestFilter {
    private static final Logger log = LoggerFactory.getLogger(RequestLogFilter.class);
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        // 教学服务生成自己的编号，不直接相信客户端提供的编号。
        String requestId = UUID.randomUUID().toString();
        request.setAttribute("requestId", requestId);
        response.setHeader("X-Request-ID", requestId);
        MDC.put("requestId", requestId);
        long start = System.nanoTime();
        try {
            chain.doFilter(request, response);
        } finally {
            log.info("method={} path={} status={} durationMs={}", request.getMethod(), request.getRequestURI(),
                    response.getStatus(), (System.nanoTime() - start) / 1_000_000);
            MDC.remove("requestId");
        }
    }
}

沿着 doFilterInternal 读：生成编号，放进 request 和响应头，把请求交给后面，最后记录耗时并清理 MDC。重启后用 curl -i 查询列表，可以看到 X-Request-ID。错误正文也会获得同一个编号。日志显示格式在下一篇集中配置。
