12 / 从终端任务清单走向网页

第五课：登录一次，为什么能记住我？

用户第一次登录后，再点“查看任务”，网站怎样知道应该返回谁的任务？

HTTP 请求本身不会自动继承上一次请求的用户身份。服务器可以让客户端带上凭证，再据此识别用户。我们先用一个容易理解的例子：登录后领一张随机编号的小票，以后带票查询。

1. Cookie：浏览器怎样保存和携带小票？

登录成功后的响应头示意：
Set-Cookie: sid=random-ticket; Path=/; HttpOnly; Secure; SameSite=Lax

以后符合规则的请求可能带上：
Cookie: sid=random-ticket

Cookie 是浏览器保存和发送小数据的一种机制。Set-Cookie 告诉浏览器保存；以后域名、路径、协议等条件符合时，浏览器自动携带。Cookie 里可以存会话编号，也可以存其他小信息，它本身不等于完整登录方案。

HttpOnly 限制网页 JavaScript 直接读取这个 Cookie；Secure 要求通过安全连接发送；SameSite 控制跨站场景下的携带规则。示例面向 HTTPS 网站。正式登录 Cookie 应明确设置这些属性，并按业务选择有效期。

2. Session：服务器怎样认出编号？

登录验证通过后，服务器建立一条记录：“小票 A 对应用户小明，有效到某个时间。”浏览器带上 A，服务器找到记录，就知道用户身份。这条服务端会话记录通常叫 Session，记录可以保存在内存、数据库或 Redis 等地方。

浏览器保存 sid=A → 请求带 Cookie → 服务器查 Session A → 得到用户编号

退出登录时，服务器可以删除或作废会话，并让浏览器清除 Cookie。若应用部署了多个实例，会话通常需要共享，或采用明确的会话路由策略。否则一次请求能找到会话，换个实例就可能找不到。

3. Token：把“凭证”当作一个统称

Token 是客户端提交的凭证。它可以是一段不透明的随机字符串，也可以是带结构的数据。Session 编号本身也可以看作一种 Token。传递方式可以是 Cookie，也可以是请求头：

Authorization: Bearer <访问令牌>

Bearer 表示持有这个有效令牌就可以按它的权限使用接口。因此令牌不能公开给其他人。Cookie 是一种携带机制，Session 是服务端会话方案，Token 是凭证概念，这几个词可以出现在同一套系统里。

4. JWT：把部分信息装进令牌，并签名

常见的签名 JWT 由三段组成：头部、载荷、签名。载荷可以写用户编号、有效期等声明；服务器验证签名和相关声明，确认令牌是否可以接受。头部和载荷通常能被解码阅读，签名并没有把内容加密，因此不应把密码等秘密放进载荷。

JWT 便于不同服务按约定验证凭证，但服务端必须验证签名、允许的算法、过期时间、签发方和接收方等。若用户要立刻退出或令牌泄漏，仅等待有效期结束可能不够，还要设计撤销、短有效期或刷新凭证等机制。

先想一想

把 JWT 放进 Cookie，它就变成 Session 了吗？

展开解释

它仍然是 JWT 格式的令牌，只是通过 Cookie 携带。令牌格式、传递方式、服务端是否保存会话状态，是不同的选择。

5. 你的任务清单现在应该怎么选？

若将来做一个普通单站点网页，先学习“随机 Session 编号 + 安全 Cookie”通常较直观：服务端能管理会话和退出。多个 API 客户端或服务间验证时，再根据需求考虑其他 Token 方案。先把身份与权限流程做正确，之后再选合适格式。

浏览器自动携带 Cookie，意味着网站还需要考虑跨站请求伪造，例如使用合适的 SameSite 设置与 CSRF 防护。把凭证放到 JavaScript 可读的本地存储，又会增加脚本漏洞泄露凭证的风险。实际登录应采用成熟框架，不要在学习接口时自行拼装完整认证系统。

6. 认出用户以后，还要检查任务归谁

假设小明登录后请求 DELETE /api/tasks/8。服务器不仅检查“是否登录”，还要确认编号 8 的任务属于小明，或他具备相应管理权限。仅仅知道一个任务编号，不能代表有权删除它。
