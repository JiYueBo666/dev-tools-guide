从终端任务清单走向网页

网站怎样记住你已经登录

今天打开网页，它显示你的任务。它怎样知道是你，而不是昨天用过这台电脑的另一个人？

网页第一次把用户名和密码交给后端，后端验证通过。过一会儿，你再点击查看任务，后端收到的是一条新的请求。它需要从这条请求里找到某种凭据，才能认出你。

我们可以从存包处的小票想起：工作人员核验后给你一张编号票，以后你出示票，对方按编号找到对应记录。登录系统也常采用这样的办法。

小票留在哪里，下次谁来带？

服务器可以在登录成功的响应里，请浏览器保存一小段数据。以后访问符合条件的地址，浏览器自动带上它。这种保存和携带小数据的机制叫 Cookie。

登录成功的响应示意：
Set-Cookie: sid=random-ticket; Path=/; HttpOnly; Secure; SameSite=Lax

以后的请求可能带上：
Cookie: sid=random-ticket

这张 Cookie 中保存的是一个随机编号。服务器另外记着“这个编号对应小明，有效到什么时候”。下一次收到它，查记录就知道该返回小明的任务。服务器保存的这份会话记录通常叫 Session。

这样就不用每次查询任务都重新提交密码。Cookie 负责把编号带来，Session 帮助服务器按编号找到已验证的身份。Cookie 也能保存其他小信息，不是只有登录才能用。

退出登录时，哪边要处理？

服务器可以让 Session 失效，浏览器也清除相应 Cookie。只有删掉浏览器里的票，而服务器仍接受它时，别人拿着复制的有效票仍可能使用。因此退出、过期和失效需要一起设计。

如果 Java 应用有多个实例，记录只留在其中一个实例的内存里，请求换到另一个实例可能就找不到。会话可以放在共享存储中，或采用明确的请求路由安排。

小票怎样少一些泄露机会？

示例里的 HttpOnly 限制网页脚本直接读取 Cookie；Secure 要求通过安全连接发送；SameSite 控制跨站情形下的携带。这份示例用于 HTTPS 登录场景，具体有效期和 SameSite 策略需要按业务设置。

浏览器自动带票很方便，也意味着另一个网站可能试着诱导浏览器向你的网站发操作请求。因此使用 Cookie 登录时，还要考虑 CSRF 防护，例如合适的 SameSite 与 CSRF 校验。服务端始终要检查此次操作是谁发起、是否有权执行。

Token 和这张票有什么关系？

Token 可以理解成提交给服务端的凭证。它可能是一段随机文字，也可能带有结构。Session 编号也属于凭证的一种。除了放在 Cookie 里，还可以由客户端写进请求头：

Authorization: Bearer <访问令牌>

Bearer 的意思是，持有这个有效令牌就能按它的权限访问。因此客户端要保护它。Cookie 讲的是怎样携带，Session 讲的是服务器怎样保存会话，Token 讲的是用来证明访问资格的凭证，它们可以出现在同一套方案里。

如果票上自己带着一些信息呢？

某些系统希望多个服务都能验证凭证，于是让凭证带上用户编号、有效期等声明，再加上可验证的签名。常见的签名 JWT 就采用这种方式，通常分为头部、载荷和签名三段。

服务端验证签名以及相关声明，判断这份令牌能否接受。载荷通常可以被解码阅读，签名没有把内容加密，所以密码等秘密不该放进去。验证时还要检查算法、有效期、签发方和接收方等，不能只把内容解码出来就认为可信。

JWT 让一些跨服务验证更方便，但立刻撤销可能需要额外安排。比如令牌尚未到期，用户已退出，就要考虑撤销记录、短有效期或刷新凭证机制。JWT 也可以通过 Cookie 携带，选择格式和选择存放方式是不同的决定。

你的任务清单以后怎么走？

如果做普通的单站点网页，可以先学习随机 Session 编号配合安全 Cookie，这样退出和会话管理比较直观。确实有多个客户端、多个服务等需求时，再选择适合的 Token 方案。实际认证应采用成熟框架，避免自行拼装密码验证和令牌校验。

无论选哪种，都还有最后一道检查：小明登录后请求删除任务 8，后端必须检查任务 8 是否属于小明，或他是否有管理权限。认出一个人和允许他办一件事，需要分别判断。
