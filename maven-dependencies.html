项目要用 Gson，Maven 怎样把它接进来

你已经能编译自己的类了。现在让这个小程序使用别人写好的类，看看新增的工作在哪里。

Hello 只用 Java 自带的输出功能，JDK 已经提供了它。想把任务变成 JSON，就要使用 Gson。Gson 也由许多 Java 类组成，只是这些类由别人编译和发布好了。

这些类常被装在一个 JAR 文件里。JAR 可以理解成按 Java 工具约定组织的归档文件，里面装着类和资源。要使用 Gson，编译和运行时都得能找到这份库。Maven 帮我们根据清单获取它，并在需要时准备依赖路径。

先说明要哪个库

回到上一篇的 pom.xml。在 properties 结束之后、build 开始之前，增加 dependencies：

<dependencies>
    <dependency>
        <groupId>com.google.code.gson</groupId>
        <artifactId>gson</artifactId>
        <version>2.15.0</version>
    </dependency>
</dependencies>

Gson 的这组三项是它的发布身份。你自己的项目有一组身份，依赖也有一组；Maven 根据组、名字和版本找到对应产物。这些值从 Gson 官方说明查，不需要猜名字。

以后加 MySQL 驱动，就在同一个 dependencies 里面再添一段 dependency。项目仍只有这一份主 pom.xml，已有的 build 等部分保留。

写 import 时，库还没凭空出现

把 Hello.java 改成下面这个完整程序：

package com.example.notes;

import com.google.gson.Gson;
import java.util.Map;

public class Hello {
    public static void main(String[] args) {
        Gson gson = new Gson();
        String json = gson.toJson(Map.of("content", "喝水"));
        System.out.println(json);
    }
}

import com.google.gson.Gson 让编译器知道 Gson 这个短名称指向哪个类。它不下载类，也不创建对象。pom.xml 中的依赖让 Maven 获取库，import 帮源码识别类名，new Gson() 才创建转换工具。这三处做的是同一条路上不同的工作。

java.util.Map 由 JDK 提供，不必增加外部依赖。Map.of 在这里创建一项键值对应关系，Gson 再把它写成 JSON。程序运行后应看到 {"content":"喝水"}。

为什么只改依赖，还需要再编译

执行 mvn compile，Maven 会把新依赖纳入编译路径，编译器才能识别 Gson。Maven 通常先查本地缓存，需要时再从配置的远程仓库下载。默认常用公共仓库是 Maven Central，第一次较慢，以后很多文件可以复用。

默认本地仓库在用户目录的 .m2/repository，例如 Gson 的 JAR 会按它的组、名字和版本排列。一般不需要手动进去复制和删除文件。

一个库自己也可能需要其他库。Maven 按发布者的依赖说明继续查找，这叫传递依赖。可以在项目根目录运行 mvn dependency:tree，查看当前项目最终使用哪些库，以及它们从哪条依赖关系进来。

这次运行，为什么不能只用原来那条 java 命令

上篇的 -cp target/classes 只指向你编译出的类。Gson 位于另一份 JAR 中，运行时也需要找到它。如果编译成功却运行时报 NoClassDefFoundError，可能就是运行时类路径缺了外部库。

可以让 Maven 的执行插件帮忙准备项目依赖后启动 main。先在 build/plugins 中，放到已有 compiler 插件之后，增加：

<plugin>
    <groupId>org.codehaus.mojo</groupId>
    <artifactId>exec-maven-plugin</artifactId>
    <version>3.5.0</version>
</plugin>

然后在根目录运行：

mvn compile exec:java -Dexec.mainClass=com.example.notes.Hello

compile 先编译，exec:java 再调用执行插件，-Dexec.mainClass 指定入口类。这里执行插件负责准备运行环境，它没有被写进你的业务代码里。后面的 Spring Boot 插件也承担类似的构建与启动辅助工作，只是会准备 Web 应用需要的环境。

依赖和插件，放在不同位置是有原因的

Gson 是程序运行时要调用的工具，所以写在 dependencies。compiler 和 exec 由 Maven 在构建或执行阶段使用，所以放在 build/plugins。看一段配置时，可以先问：是业务代码要用它，还是 Maven 要用它来办事？

还有一些库只在特定阶段需要。scope 为 test 的测试库参与测试编译和测试运行，通常不进入正式应用的运行依赖；runtime 常用于源码没有直接引用具体类、但运行时需要的实现，比如某些数据库驱动。没有写 scope 的普通依赖默认是 compile 范围。

换版本和排错，也要看清是哪一层

库的版本冲突时，Maven 会按依赖规则选择最终版本，不能只看你在一处写了什么。dependency:tree 能帮助检查，最终选择也可能受依赖管理影响。先看清问题，再决定是否统一版本或排除某条传递依赖。

如果 IDE 提示找不到 com.google，先看 mvn compile 能否通过。Maven 通过而编辑器仍报红，可能是 IDE 没有导入整个 Maven 项目；确认打开的是含 pom.xml 的根目录。若 Maven 本身也下载失败，则看网络、仓库与报错的依赖坐标。两种情况需要处理的位置不同。
