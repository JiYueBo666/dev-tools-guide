改完代码，怎样知道旧功能还好？

你不想每次改一个方法，就从添加任务到删除任务手动点一遍。

手动试一次很直观，但功能变多后容易漏。自动测试把“发什么请求、应该收到什么”写下来，每次改完让电脑重复检查。它保留的是你对行为的约定。

先从一条最重要的路径开始：添加任务，按返回地址查到它，标记完成，再删除。下载示例已经把这条路径放在 src/test/java/com/example/todo/TaskHttpTest.java 中。

请求可以在测试里发给框架

MockMvc 会把模拟请求交给 Spring MVC 的处理链，让路由、JSON 转换、校验、异常处理等一起参与，但不需要为测试监听真实端口。它对应图片里 httptest 的一类使用目的。

mvc.perform(post("/api/tasks")
        .contentType(MediaType.APPLICATION_JSON)
        .content("{"content":"学习框架"}"))
    .andExpect(status().isCreated())
    .andExpect(jsonPath("$.content").value("学习框架"));

这是 TaskHttpTest 方法内部的一段。perform 发模拟请求，andExpect 写预期：状态是 201，响应 content 是刚才发的文字。如果有人以后把成功码改错或丢掉内容，这个检查会失败。

Spring Boot 4 的 Web MVC 测试使用 spring-boot-starter-webmvc-test。示例中的 @AutoConfigureMockMvc 来自 org.springframework.boot.webmvc.test.autoconfigure，不要把其他大版本教程的包名直接混进来。下载包已经配好相关 import 与依赖。

同一条规则，用几种输入检查

空字符串、纯空格、缺少字段和损坏 JSON 都应该被拒绝。可以把这些输入放到参数表里，让同一个测试逐项执行。这是表格驱动测试的思路，JUnit 可以用 @ParameterizedTest 与 @ValueSource 表达。

这些输入不只是为了增加测试数量。它们分别检查读取正文与校验规则的边界。有效内容应该成功，格式或内容不合适应该返回 400，找不到任务应该返回 404。围绕行为和失败情况选测试，比重复断言每个私有方法更有用。

在含 pom.xml 的目录运行 mvn test。全部通过，Maven 最后显示 BUILD SUCCESS。测试本身不启动你的 MySQL，也不连接原项目的数据。

内存测试通过，数据库就一定没问题吗？

还不能据此确认 SQL、表结构和事务。它们需要另外的数据库集成测试。可以用 Testcontainers 启动一次性 MySQL 容器，让测试建表、写入、检查，结束后丢弃；也可以明确使用专用测试库，并对初始化和清理作出安排。

测试账号不应有权限写入你的日常任务库。测试前核对实际数据源配置，比约定大家“别写错库名”更可靠。使用 H2 跑得过，也不代表 MySQL 的方言、约束与锁行为完全相同。

为什么加了回滚，数据库还是留下了数据？

测试方法上的事务一般绑定当前线程。真实 HTTP 测试如果启动随机端口，客户端和服务端在不同线程处理，它们可能使用不同事务。测试线程结束回滚，不会自动撤销服务器已经提交的写入。

所以要按测试方式设计隔离：同线程的数据库测试可以使用测试事务回滚；真实服务请求则使用独立测试库、每例清理、唯一数据或一次性容器。异步任务和 REQUIRES_NEW 事务也要单独考虑。

到这里，项目具备了什么？

接口有约定，输入有检查，错误有一致回复，日志能找到同一条请求，保存层可以替换，关键行为有自动检查。接下来把原有 TaskDao 接入时，你可以先替换保存层，再用这些行为检查确认接口仍然履行原来的约定。
