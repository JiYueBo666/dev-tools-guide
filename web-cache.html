从终端任务清单走向网页

没有变化的内容，留一份就好

任务变了，网页要更新。但那张从来没变过的图标，为什么也要重新下载？

假设你每天都看同一本课本。第一次需要拿到整本书，以后翻到同一页，直接看手里的这本就行。如果每天都从印刷厂重新取一本，实在没必要。

浏览器也会把用过的样式、图片等内容留一份。下次再用，可能直接取这份副本。这能节省流量，也能让页面更快出现。接下来的问题才真正重要：手里的这一份，还能信吗？

给副本一个可以直接用的期限

服务器返回一张图时，可以附上一句“这份内容在一段时间内可以直接使用”。写到 HTTP 中，例如：

Cache-Control: public, max-age=30

max-age 给出 30 秒的新鲜期。副本还新鲜时，浏览器可以直接使用，不必再下载完整内容。public 允许共享缓存保存它；这适合公开内容。副本的实际年龄还会考虑它在中间缓存待过多久等信息。

这类无需向服务器确认就使用新鲜副本的情形，常被叫作强缓存。名字放在后面记即可，关键是浏览器已经有一份仍被允许使用的内容。

到期了，不等于内容变了

期限过后，课本未必出了新版。浏览器可以问：“我这里的版本还是 v1，需要换吗？”如果没变，服务器只回复“继续用你手里的”，不必重新传正文。

ETag 就承担这种版本标记的作用。第一次收到内容时，浏览器连同 ETag 一起记下。以后需要确认时，把标记放进 If-None-Match：

第一次响应：
HTTP/1.1 200 OK
ETag: "tips-v1"

这里是完整内容。

以后请求时带上：
If-None-Match: "tips-v1"

如果版本相同，服务器返回 304，浏览器继续用原来的正文。版本变了，服务器返回 200、新正文和新的标记。先确认再使用的过程，常被叫作协商缓存。

你可以用实验程序看到这两种回复：

curl -i http://127.0.0.1:8081/tips
curl -i http://127.0.0.1:8081/tips -H 'If-None-Match: "tips-v1"'

第一条会拿到 200 和文字。第二条带上同一标记，会拿到 304，没有那段正文。这里是手动模拟版本确认，curl 没有替你像浏览器那样管理副本。实验版本号固定，真实服务需要让标记随内容变化。

三种安排，对应三种使用需要

有些东西可以放心直接用一会儿，于是设置 max-age。有些东西允许留副本，却每次都需要确认，于是使用 no-cache。这个名字容易让人以为“不保存”，实际重点在重新使用前验证。若要求不存储响应，则使用 no-store。

private 表示只允许用户自己的私有缓存保存，公共代理等共享缓存不应保存。比如你的任务列表属于你自己，不能让另一个用户从公共缓存拿到。实验的任务接口使用 no-store，便于把注意力放在请求本身。

样式文件则可以采用另一种安排：文件名包含内容指纹，例如 app.a81f.css。改了内容，名字也改变，网页就去取新地址；旧地址的内容可以保存很久。

为什么发布了修改，看起来还没变？

有时服务器已经有新文件，浏览器还在用新鲜副本。可以在 Network 面板看它是否来自内存或磁盘缓存，再看响应的 Cache-Control 和 ETag。开发时可以临时勾选 Disable cache；发布时则要规划缓存期限和资源版本。

同样是“复用”，直接使用副本省掉了网络确认，304 主要省掉正文传输。明白这个区别以后，看到缓存命中和 304，就能知道浏览器省下了哪一段工作。
