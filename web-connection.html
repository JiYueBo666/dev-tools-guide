第三课：发请求前，电脑先做了什么？

打开网页并不只有传送 HTML 这一个动作。第一次访问时，双方还要建立连接和约定如何安全通信。

想象你准备给远处的人连续递送几份文件。需要先找到地址，确认双方能通信，再决定怎样保护内容。网络也有相似的准备步骤。对于常见的 HTTPS over TCP 访问，可以按下面的顺序理解：

域名解析 → TCP 建立连接 → TLS 安全协商 → HTTP 请求与响应

DNS 把域名转换成可连接的地址。TCP 提供有序、可靠的字节传输。TLS 负责保护内容并验证对端身份。HTTP 约定这些字节里表达什么请求和响应。HTTP/3 使用 QUIC，连接流程不同；这里先理解 HTTP/1.1 和 HTTP/2 常见的 TCP 路径。

1. TCP 为什么要三次握手？

客户端                          服务器
   ── SYN：请求建立连接，给出起始序号 ──>
   <── SYN + ACK：确认，并给出自己的序号 ──
   ── ACK：确认收到对方起始信息 ──>

客户端发出连接请求，服务器确认并给出自己的起始信息，客户端再确认收到。这样双方可以同步起始序号等连接状态。序号帮助接收端整理顺序、识别缺失的数据，再按需要重传。

这三次消息不是 HTTP 的 GET 或 POST，也不表示完成登录。它们是在准备传输通道。TCP 负责可靠传输，应用仍需要处理服务失败和业务重试。

2. 关闭时为什么常说四次挥手？

TCP 两个方向可以分别结束。客户端说“不再发送了”，服务器先确认；服务器处理完自己的发送，再说“我也发送完了”，客户端确认。所以常见示意是 FIN、ACK、FIN、ACK 四步。某些消息可以合并，实际抓包不一定恰好四个包。主动关闭的一侧通常还会经历 TIME_WAIT，处理迟到数据和最后确认的重传。

3. HTTPS 多做了什么？

如果直接传密码，网络中间节点可能读到内容。HTTPS 在 HTTP 外增加 TLS 保护。一次常见 TLS 1.3 完整握手中，客户端先给出支持的参数和密钥交换信息，服务器选择参数并发送证书、相应的密钥交换信息和证明。

浏览器检查证书是否受信任、是否有效、域名是否匹配，并验证对方对密钥的持有证明。双方通过协商产生加密通信需要的密钥，交换完成消息后继续发送应用数据。具体消息数量会受版本和连接恢复影响。你先记住三个目的：确认对端、协商密钥、保护之后的通信。

先想一想

网站用了 HTTPS，就说明这个网站值得信任、不会骗人吗？

展开解释

HTTPS 保护与目标站点之间的通信，并帮助验证站点身份。网站提供什么业务、怎样处理数据，仍由网站自己决定。

4. 每张图片都重新建立连接，会怎样？

一页有几十个资源，反复握手会增加等待。HTTP/1.1 默认允许持久连接，在同一连接上继续发送请求，常称 keep-alive。它减少重复建立连接的成本；这与 TCP keepalive 探测空闲连接的机制是两件事。

浏览器通常还会同时建立多个 HTTP/1.1 连接，提高资源加载速度。HTTP/1.1 的同一连接存在响应顺序等限制，某个慢响应可能让后面的响应等待。

5. HTTP/2 怎样让多份内容交错传送？

HTTP/2 把消息拆成帧，用不同的流编号区分请求。一个连接里，不同请求的帧可以交错传送，接收方再按流编号拼回去，这就是多路复用。它减少应用层的排队，但仍然运行在 TCP 上；TCP 丢失的数据等待重传时，其他流也可能受影响。

可以把浏览器 Network 的 Protocol 一列打开，看当前网站使用 http/1.1、h2 还是 h3。协议由服务器支持情况和连接协商决定。多个请求共享连接，也不等于它们都能无条件同时占满带宽。
