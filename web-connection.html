消息怎样安全地走到远处

浏览器知道要说什么以后，还要先找到对方，建立一条能够交谈的路。

在自己的电脑里调用一个方法，数据直接交给同一程序里的另一段代码。发往远处服务器就多了几件事：地址要找对，丢了的数据要补上，内容还要避免被路过的人读到。

对于常见的、运行在 TCP 上的 HTTPS 连接，可以按这条路理解：先通过 DNS 找地址，再建立 TCP 连接，然后进行 TLS 安全协商，最后交换 HTTP 请求和响应。HTTP/3 使用 QUIC，连接流程有所不同，我们先把前面这条常见路径讲清楚。

先确认双方都准备接收

TCP 建立连接时，客户端先发出一条 SYN，带上自己的起始序号。服务器回复 SYN 和 ACK，确认收到了，同时给出自己的起始信息。客户端再用 ACK 确认对方的信息。

客户端  ── SYN ─────────>  服务器
客户端  <─ SYN + ACK ────  服务器
客户端  ── ACK ─────────>  服务器

这三次消息帮助双方同步连接状态，所以叫三次握手。起始序号等信息让后续数据能够按序组织，发现缺失时可以重传。此时还没完成网站登录，双方是在准备传输数据。

TCP 让应用得到有序、可靠的字节传输。应用本身是否处理成功，仍要由 HTTP 回复和业务逻辑来说明：例如连接正常，数据库也可能拒绝一次写入。

连上以后，还要保护谈话内容

如果把登录密码直接放进明文消息里，沿途能接触流量的人可能读到。HTTPS 使用 TLS 保护后面的交谈。

在一次常见的 TLS 1.3 完整握手中，客户端先告诉服务器自己支持的参数，并提供密钥交换信息。服务器选择参数，返回证书以及完成密钥交换、证明身份所需的信息。浏览器会检查证书是否受信任、是否在有效期内、是否对应当前域名，并验证服务器对密钥的持有证明。

双方随后得到本次通信使用的加密密钥，交换完成消息，再继续发送受保护的数据。你不必先记住所有消息名，先理解为什么要做这段准备：浏览器要确认自己连到了目标站点，双方要准备能保护谈话内容的密钥。

连接恢复和不同 TLS 版本会改变具体步骤。HTTPS 保护通信，也帮助验证站点身份；站点本身提供什么服务，还要由使用者另行判断。

一页有几十个文件，能不能沿用这条路？

任务页面不仅有 HTML，还有样式、脚本和图标。如果每个文件都从头连接、握手，等候就会重复很多次。HTTP/1.1 默认支持持久连接，后面的请求可以继续使用已有连接，这通常叫 keep-alive。

同一连接在一段时间里承接多次请求，就能减少重复准备的成本。TCP 也有一个叫 keepalive 的空闲连接探测机制，那是另一项功能；这里关注的是 HTTP 请求复用连接。

HTTP/1.1 的同一连接存在响应顺序等限制，慢响应可能让后面的响应等待。浏览器通常会建立多个连接，让不同资源同时加载，但连接数量仍有限。

HTTP/2 让几份内容交错传送

HTTP/2 把消息拆成小帧，每个请求分配一个流编号。一个连接上可以交错传送多个流的帧，接收方再按编号整理回来。这就是多路复用。

像几封长信拆成标好编号的信页，交替运送，就不用等一封全部结束后才轮到下一封。HTTP/2 减少了应用层的排队，但底层仍是 TCP；TCP 丢失一段数据、等待补齐时，这个连接上的多个流仍可能受影响。

打开浏览器 Network 的 Protocol 一列，可以看到网站实际使用 http/1.1、h2 或 h3。它们由客户端和服务端支持情况及连接协商决定。

谈完以后，两个方向分别收尾

TCP 允许双方分别结束自己的发送。客户端可以先说“我不再发送”，服务器确认后，仍可能把剩余数据发完；发完后服务器也告知结束，客户端再确认。因此常见过程画成 FIN、ACK、FIN、ACK，叫四次挥手。

实际消息可能合并，不一定正好看到四个包。主动关闭的一侧通常还会进入 TIME_WAIT，以处理最后确认的重传和迟到数据。把关闭理解成双方分别完成发送，比硬记四个名字更容易串起过程。
