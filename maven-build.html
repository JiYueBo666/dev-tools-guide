SPRING BOOT 之前 / MAVEN

编译、测试、打包，最后怎样跑起来

Maven 的命令很多。先把它们放回一个程序交付前会经历的过程，就容易理解了。

你把代码写好，通常要确认它能编译、关键行为没坏，再整理成便于交付的文件。这些工作有先后顺序。Maven 把常见构建步骤排在一起，你指定想走到哪里，它就执行之前需要经过的阶段。

想要一个包，不必逐条输入每一步

常见顺序可以先看成：compile 编译，test 执行相应测试，package 生成分发产物，verify 执行已配置的进一步检查，install 把产物放进本地仓库供其他项目使用。这条主构建生命周期里还有资源处理等中间阶段。

运行 mvn package，会先经过编译、测试等前置阶段。因此不必先 mvn compile，再 mvn test，最后 mvn package。没有测试文件时，走到测试阶段也不代表检查过业务功能；真实运行了什么，要看测试配置和报告。

mvn clean 用于清理 target 等配置的构建输出。它属于另一套清理生命周期，和 package 连用时写 mvn clean package：先清理，再从头构建。它通常不删除源码和本地依赖缓存，也不保证替你清掉程序生成的所有外部文件。

install 为什么不是“把 Maven 装进电脑”？

你安装 Maven 用过 brew install maven，那是在操作系统里安装工具。mvn install 则是让 Maven 构建当前项目，再把产物放进本地 Maven 仓库，供别的项目引用。两个 install 的执行者和目的不同。

同样，Maven 生命周期里的 deploy 通常指把构建产物发布到远程产物仓库，不等于把 Web 服务启动到服务器上。看到命令时，要结合这个工具的语境理解。

为什么有的命令中间有冒号？

compile 是生命周期阶段，执行到那里时会调用绑定的工具。exec:java 则直接表示“exec 插件中的 java 目标”。spring-boot:run 也是一个插件目标。插件提供具体做法，生命周期提供构建顺序，两者合起来完成工作。

这些设置通常在 pom.xml 中，因此换一台电脑后，Maven 仍能根据同样的说明准备构建。首次获取插件时出现下载信息是正常过程。

package 生成 JAR，为什么 java -jar 可能不能直接运行？

在 maven-notes 根目录运行 mvn package，通常会生成 target/maven-notes-1.0-SNAPSHOT.jar。这个普通 JAR 保存项目的类与资源，默认不一定有 main 的入口声明，也不一定把 Gson 等依赖打进去。

所以拿到一个普通 JAR，不能仅凭扩展名就认定 java -jar 可以启动。若出现“没有主清单属性”，通常是没有声明可执行入口；若缺类，则需要检查运行依赖。普通库 JAR、本地执行 main 和可独立交付的应用包，准备方式会有差别。

Spring Boot 为什么又多出 parent 和插件？

下一部分的 pom.xml 采用 spring-boot-starter-parent。父项目集中管理相互配合的依赖版本、构建默认值和部分插件设置，子项目沿用这些安排，减少自己组合版本的工作。

dependencies 决定实际引入哪些库。父项目管理了版本，不等于已经把所有 Spring 功能加进程序；需要 Web 时仍然要写 spring-boot-starter-webmvc，需要校验时再写 validation starter。starter 把一组常用组件整理成入口依赖。

spring-boot-maven-plugin 负责 Spring Boot 相关的构建目标。在采用该父项目并声明插件的常见配置下，package 时会安排 repackage，把应用组织成可执行的 Boot JAR，包含启动所需的应用与依赖。这样的包才适合用 java -jar target/对应文件.jar 启动。

不要把这种打包能力当成所有普通 Maven 项目的默认行为。你在 pom.xml 里能找到它的来源：父项目的构建安排和声明的插件。

以后怎样读一份新的 pom.xml

先看项目的名字和父项目，再看 dependencies，知道业务代码得到哪些工具；然后看 build/plugins，知道编译、测试和打包怎样安排。有需要时再看 properties、profiles 和更复杂的依赖管理。

想知道继承后真正生效的配置，可以用 mvn help:effective-pom 查看合并后的 POM。输出可能很长，它适合排查“这个默认值从哪里来”，不需要从第一行读到最后一行。

你也会看到 mvnw 和 mvnw.cmd，它们是 Maven Wrapper 启动脚本，让项目使用约定的 Maven 分发版本。仓库内还需有对应的 .mvn/wrapper 配置，不能只自己创建一个同名空文件。当前练习已经安装 Maven，可以继续用 mvn。

如果构建提示 release version 21 not supported，检查 mvn -version 显示的 Java。Maven 可能通过 JAVA_HOME 使用了另一个 JDK，与终端 java -version 的结果不同。运行环境这一步要对上，编译配置才有意义。

回到自己的项目时，你应该能顺着说明找出：源码在哪里，程序用什么外部库，哪部分配置交给 Maven，哪一条命令负责运行。理解这些，再进入 Spring Boot，就不会把整个工程当作一块打不开的盒子。
