代码变短以后，数据库还在做什么？

把一次查询写成一个方法名很方便，但我们仍要知道它最终做了多少工作。

你用 ORM 后，很多 SQL 不再出现在业务文件里。它们依然会执行，只是由工具生成。问题往往出在“看起来只调用了一次，背后却做了很多次”。我们用任务清单把这些现象串起来。

查了 20 条任务，为什么发出 21 次查询？

假设每条任务都关联一个创建者。先查任务列表是一条 SQL，显示时又逐个读取创建者；如果每次触发一条查询，20 条任务就可能额外查询 20 次。这就是 N+1 问题。

开发时可以在专用环境观察 SQL 数量，确认是一次取齐，还是遍历中不断补查。JPA 中可以按具体页面使用 EntityGraph、fetch join 或 DTO 投影取得所需数据。不能只看到设置 EAGER 就认为已解决，急切加载本身不保证合成一条 SQL；集合 fetch join 还要注意分页和重复结果。

你的第一版 TaskEntity 没有关联，因此不会凭空出现这个“任务查创建者”的 N+1。等增加关联时再用这个例子检查，避免为了演示而给小项目塞一堆表。

想把 true 改回 false，为什么有人说零值会被跳过？

GORM 等工具的某些更新接口会忽略结构体零值，Java JPA 的受管理实体没有同样的默认规则。比如 done 从 true 改成 false，只要确实在事务中修改了受管理实体，通常会被检测并写回。

Java 里更常见的问题是更新请求用了 boolean：用户没发 done，与用户明确发 false，看起来都是 false。需要区分“没提供”与“提供了 false”时，可以使用 Boolean 或专门的 PATCH 数据结构，明确规定 null 表示什么。更新时逐个决定哪些字段可以改，别把缺省值误写到现有记录。

删除后为什么数据还在？

有些系统希望任务能恢复，就增加 deletedAt 等字段。删除动作改成记录删除时间，查询时排除这类记录，这叫软删除。好处是能保留记录，代价是每种查询、唯一约束、恢复操作都要考虑它。

Spring Data JPA 不会因为你随便加了一个时间字段就自动完成软删除。需要明确实现删除与过滤，或采用经过配置的 Hibernate 支持。唯一名称等约束还可能被旧记录占用，所以设计恢复与重复创建规则要一起考虑。

两次写入，应该一起成功还是一起失败？

完成任务后，假设还要记录一条操作历史。如果任务已完成，历史却写入失败，数据就只做了一半。事务可以把相关数据库写入放在同一提交边界内：成功一起提交，失败按规则回滚。

@Transactional 默认传播方式 REQUIRED：没有事务就创建，有已有事务就加入。REQUIRES_NEW 则另开独立事务，外层失败不代表它一定回滚，也会额外占用连接。只有确实需要独立提交的事情，才选择这种安排。

Spring 常见代理模式下，同一个类用 this 调自己的事务方法，可能绕过代理，导致方法上的事务设置没有按预期生效。尽量让业务入口经由 Spring 管理的组件调用，并明确事务放在哪里。默认通常对 RuntimeException 和 Error 回滚，受检异常要按业务配置 rollbackFor；捕获异常后什么都不做，还可能让事务正常提交。

一次导入一千条，saveAll 就一定是一条 SQL 吗？

不一定。saveAll 方便表达多条保存，是否真正批量发送取决于 Hibernate、JDBC、编号策略和配置。IDENTITY 自增常会限制插入批处理。要减少往返，需要观察实际 SQL 和驱动行为，而不能只从方法名判断。

可在合适场景配置 hibernate.jdbc.batch_size、使用明确的批量 JDBC，或采用专门导入方案。大批数据还要分块 flush/clear，控制持久化上下文占用的内存，并规划事务大小、失败后的重试与唯一约束。先保证每条数据处理正确，再验证批量性能。

这些问题有一条共同线索：对象上的一次操作，最终仍要变成数据库的读写。看生成的 SQL、事务范围与数据变化，才能知道“简写”背后实际发生了什么。
