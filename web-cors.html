浏览器为什么要管住网页

一个网页可以向外发请求，但它不能随意读走你在别的网站里的资料。

想象你同时打开了任务网站和一个陌生网页。你在任务网站已经登录，浏览器里留着相应凭证。如果陌生网页能直接读取任务接口，你的私人清单就可能被它拿走。

浏览器要处理这种情况：同一个浏览器里，不同网站的网页不能随意读彼此的数据。因此，它会区分一段网页来自哪里，再决定是否把响应交给这段网页脚本。

地址里哪些部分决定“来自哪里”？

浏览器比较协议、主机名和端口。三者相同才算同源，路径不同没有关系。所以同一站点的 /a 和 /b 可以同源；8080 和 8081 端口不同，就属于不同来源。localhost 和 127.0.0.1 虽然可能指向同一台电脑，主机名不同，仍然跨源。

这也解释了为什么本地开发容易遇到跨域：页面由一个开发服务提供，Java 接口由另一个端口提供。双方明明都是你写的，浏览器仍然按地址规则处理。

终端能读，网页却读不到

默认启动实验程序，打开 http://127.0.0.1:8080，再点击读取任务。页面会提示无法读取响应。你在另一个终端访问 http://127.0.0.1:8081/api/tasks，却可以拿到任务。

这里差在谁接收结果。curl 直接把结果交给你；浏览器则要决定能否把 8081 的响应交给来自 8080 的网页脚本。当前没有获得允许，所以网页读不到。某些请求可能已经到达服务器，不能把跨域报错一律理解为“根本没有发出去”。

服务器可以明确同意

当网页和接口确实要分在两个来源时，接口可以在响应中写明允许的网页来源：

Access-Control-Allow-Origin: http://127.0.0.1:8080

浏览器看到来源符合，便可以把结果交给网页。这套通过 HTTP 头协商跨源读取的机制叫 CORS。

停止实验服务，然后用 ALLOW_CORS=1 java HttpPractice 重新启动。这个环境变量是实验代码自己定义的开关。再点击 GET，页面就能显示任务；在 Network 中可以看到允许来源的响应头。

有些请求，浏览器要先问一句

点击发送 JSON 的按钮时，可能先看到 OPTIONS，然后才看到 POST。原因是这份 POST 使用 application/json，浏览器要先确认目标服务允许这种跨源发送。

它先说明：“我来自 8080，接下来想用 POST，还想带 content-type 这个头。”这份预检请求大致包含：

OPTIONS /api/echo
Origin: http://127.0.0.1:8080
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type

服务器确认允许后，回复允许的来源、方法和头部。浏览器才继续发真正的 POST。预检失败时，真正请求通常不会发出；简单 GET 则可能已经发送，只是网页不能读取响应。成功的预检结果也可能被浏览器缓存，因此不必每次看到 OPTIONS。

为什么有些请求不先问？

常见的简单请求使用 GET、HEAD 或 POST，并且头部及其取值符合安全清单。若手动指定 Content-Type，通常限于 text/plain、application/x-www-form-urlencoded 或 multipart/form-data。JSON 和 Authorization 等常用设置往往触发预检。

这套划分决定要不要先询问。它不代替服务端的身份验证，也不决定用户有权操作哪条任务。

带登录凭证，还需要双方配合

跨源 fetch 通常需要 credentials: "include" 才会带上符合 Cookie 规则的凭证。服务端也要明确允许凭证，并指定具体来源；此时允许来源不能用星号。Cookie 的 SameSite 设置和浏览器第三方 Cookie 限制也会参与决定是否发送。

若服务器按不同 Origin 返回不同允许头，通常还要带 Vary: Origin，让缓存区分这些响应。否则，一份给某个来源准备的响应可能被错误复用。

网上有时建议加 mode: "no-cors"。这样得到的响应通常不允许脚本读取正文，无法拿它来显示任务。应当由接口配置允许来源，或通过同源入口访问。

回到最初的目的：浏览器需要保护不同网站之间的数据边界。CORS 让双方能在这个边界上明确协作。登录、任务归属检查和 CSRF 防护仍要在后端与认证设计中完成。
