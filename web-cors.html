12 / 从终端任务清单走向网页

第四课：终端能访问，网页为什么报错？

你用 curl 能读到任务，网页却显示请求失败。这时先看浏览器有没有限制网页读取响应。

1. 让问题真的发生一次

保持实验服务以默认方式运行，打开 http://127.0.0.1:8080，打开开发者工具的 Console 和 Network，然后点击“读取任务：GET”。网页会提示无法读取响应，Console 会出现 CORS 相关错误。

再在终端运行 curl -i http://127.0.0.1:8081/api/tasks，仍能看到任务。原因要从网页的来源说起：网页来自 8080，接口在 8081。浏览器对网页脚本读取另一个来源的数据有专门的规则。

2. 什么算同一个来源？

比较协议、主机名、端口，三者都相同才算同源。路径不参与这个判断。

两个地址是否同源
http://127.0.0.1:8080/a 与 /b同源，路径变化。
http://127.0.0.1:8080 与 http://127.0.0.1:8081跨源，端口变化。
http://localhost:8080 与 http://127.0.0.1:8080跨源，主机名变化。
http://todo.example 与 https://todo.example跨源，协议变化。

同源策略防止一个网站随意读取你在另一个网站中的私有信息。浏览器可以发送某些跨源请求，但默认限制网页脚本读取响应；有些请求还要先通过预检。curl 没有执行这套浏览器读取限制，所以它成功并不能说明网页也有读取权限。

3. 由谁允许跨源读取？

服务器可以在响应中声明允许哪个网页来源读取，这套机制叫 CORS。例如接口响应带上：

Access-Control-Allow-Origin: http://127.0.0.1:8080

现在停止实验服务，带一个环境变量重新启动：

ALLOW_CORS=1 java HttpPractice

这个变量是实验程序自己约定的开关，会让接口响应允许 8080 的来源。重新点击 GET 按钮，网页就能显示任务。在 Network 中比较响应头，确认多了允许来源的字段。

4. 为什么发送 JSON 前多了一条 OPTIONS？

点击“发送 JSON：POST”。Network 中通常先出现 OPTIONS，再出现 POST。application/json 的 Content-Type 不属于 CORS 简单请求允许的那几类，浏览器需要先向接口确认是否允许。

预检请求的关键字段：
OPTIONS /api/echo
Origin: http://127.0.0.1:8080
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type

允许时，服务器响应：
Access-Control-Allow-Origin: http://127.0.0.1:8080
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type

预检成功后，浏览器再发送真正的 POST。预检失败时，POST 通常不会发送；普通简单 GET 则可能已经到达服务器，只是响应不允许网页读取。你可以对照终端日志观察两种情况。浏览器可能缓存成功的预检结果，因此不必每次都看到 OPTIONS。

5. 怎样判断简单请求？

按常见判断，请求方法为 GET、HEAD 或 POST，且头部符合 CORS 安全清单；手动设置的 Content-Type 若存在，通常限于 text/plain、application/x-www-form-urlencoded 或 multipart/form-data。还有头部取值等限制。JSON 正文常触发预检，Authorization 等自定义认证头也会触发预检。

先想一想

在 fetch 中加 mode: "no-cors"，能不能直接读到任务 JSON？

展开解释

不能。这样通常得到不可读的 opaque 响应，脚本无法读取正文和真实状态。需要服务端提供正确的 CORS 配置，或让页面与接口同源。

6. 带 Cookie 时还要配合什么？

跨源 fetch 想带上符合 Cookie 规则的凭证，通常需要 credentials: "include"。服务端同时要返回 Access-Control-Allow-Credentials: true 和明确的允许来源，此时不能用星号作为允许来源。Cookie 的 SameSite 和浏览器第三方 Cookie 限制也会影响发送。动态按来源响应时，通常还需要 Vary: Origin 避免缓存混用。

CORS 决定网页能否读取跨源响应。服务端仍要检查用户身份和操作权限，也要处理 CSRF；允许来源不代表所有访问者都能修改任务。
