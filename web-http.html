第一课：一条任务怎么从网页发出去？

先不背 HTTP 的定义。我们先让网页向 Java 程序要一份任务列表。

1. 先分清谁做哪一部分

浏览器负责显示输入框和列表，这部分通常叫前端。Java 负责检查请求、读写数据库、整理结果，这部分通常叫后端。前端拿到结果后决定怎么显示，这叫渲染。例如同一份任务数据，可以显示成表格，也可以显示成卡片。

浏览器不直接拿数据库密码去连 MySQL。它向后端提供的地址发送请求，后端检查这次操作是否允许，再访问数据。这个可以调用的地址以及使用规则，就是我们这里说的接口。

2. 先亲眼看一次请求和响应

启动首页提供的实验服务。在另一个终端输入：

curl -i http://127.0.0.1:8081/api/tasks

你会看到 200 状态、响应头和一段任务 JSON。-i 让 curl 同时显示响应头，便于观察。这个地址现在返回固定任务，我们先只看交换信息的方式。

请求的大致样子：
GET /api/tasks HTTP/1.1
Host: 127.0.0.1:8081
Accept: */*

响应的大致样子：
HTTP/1.1 200 OK
Content-Type: application/json

[{"id":1,"content":"学习 HTTP","done":false}]

第一行说明要做什么、找哪个地址。随后是一组头部，提供附加说明。空行把头部和正文隔开，正文里放实际数据。GET 请求常常没有正文，响应则在这里带回任务列表。这是 HTTP/1.1 的文字示意；HTTP/2 在网络上的编码方式不同，方法、头部和正文这些含义仍然存在。

3. 添加任务时，文字放哪里？

查询列表时只需说明地址。添加任务时还要把“喝水”这段内容交给后端，通常把数据放进请求正文。下面是将来任务接口的约定示例，实验服务没有实现这个创建接口：

POST /api/tasks HTTP/1.1
Host: todo.example
Content-Type: application/json
Accept: application/json

{"content":"喝水","taskDate":"2026-11-12"}

Content-Type 说明本次发送的正文是什么格式；Accept 说明希望接收什么格式。application/json 告诉对方按照 JSON 规则解析。只把文字写成 JSON 的样子，却把格式标成其他类型，后端可能无法按预期处理。

可以先在实验里发送同一段文字，观察服务器是否原样收到：

curl -i http://127.0.0.1:8081/api/echo   -H 'Content-Type: application/json'   -d '{"content":"喝水","taskDate":"2026-11-12"}'

curl 使用 -d 时默认发送 POST。这个实验地址把正文作为文字返回，不保存任务，也不验证 JSON。后面的真实后端才需要解析字段、检查内容、调用 TaskDao。

4. 先约定，再分别写前后端

如果网页发 title，Java 却读取 content，双方各自的程序都可能能运行，合起来却取不到值。所以先写一份简短约定，说明地址、方法、字段和结果。前后端便可以按同一份约定开发。

要做什么接口约定示例
查看任务GET /api/tasks
查看一条任务GET /api/tasks/3
创建任务POST /api/tasks，正文带 content 和 taskDate
替换一条任务的可编辑内容PUT /api/tasks/3，提交完整可编辑字段
只修改完成状态PATCH /api/tasks/3，正文带 done
删除任务DELETE /api/tasks/3

这里把任务当作资源，用名词 tasks 表示集合，用 /3 指定其中一条，通过请求方法说明操作。这是一种常见的 RESTful 命名方式。它让地址保持一致，阅读接口时容易预测用法。

5. 网络没回音，能不能再发一次？

你点了添加，网络突然断了。任务可能没创建，也可能已经创建、只是响应丢了。直接重发 POST，可能得到两条任务。这个问题引出了幂等性：相同请求执行一次或多次，预期对服务器数据造成的最终效果相同。

GET 应用于读取；PUT 把指定资源设置为同一份内容；DELETE 删除指定资源。它们按语义是幂等的。第一次 DELETE 返回成功，第二次可能返回 404，数据层面的预期结果仍然是该任务不存在。POST 和 PATCH 不保证幂等；把 done 设置为 true 的 PATCH 可以设计成幂等，把计数加一的 PATCH 则通常不幂等。方法需要后端按约定正确实现。

先想一想

如果用户快速点击两次“创建任务”，把按钮禁用一下，是否已经解决所有重复创建问题？

展开解释

按钮禁用能改善体验，但网络重试等情况仍可能重复。需要避免重复创建时，前后端还应约定操作编号，由服务端识别同一次操作。

6. 前端怎样知道成功还是失败？

响应的状态码给出处理结果的大类，正文再说明具体原因。前端据此显示任务、提示重新登录或指出输入错误。

状态码放到任务清单里理解
200查询或修改成功，可以读取返回结果。
201已创建任务，通常返回新任务和 Location 地址。
204操作成功，没有响应正文；前端无需再解析 JSON。
400输入或请求有问题，例如 JSON 格式错误。
401 / 403401 表示需要有效身份凭证；403 表示此次访问被拒绝。
404找不到这个地址或指定任务。
409操作与当前资源状态冲突。
415后端不接受这次请求体的媒体类型。
500服务器处理发生了意外错误。

同样是失败，前端往往还要区分“任务为空”和“日期错误”。可以在 HTTP 状态码之外约定统一的业务错误结构：

HTTP 状态：400
{
  "code": "TASK_CONTENT_EMPTY",
  "message": "请输入任务内容",
  "requestId": "req-123"
}

code 供程序稳定判断，message 给人阅读，requestId 帮助到日志中找到这次请求。内部异常堆栈放在服务器日志，接口返回能指导用户操作的信息。

7. 任务多了，要怎样翻页和筛选？

GET /api/tasks?page=1&size=20&sort=id,desc&done=false

问号后面是查询参数：第 1 页、每页 20 条、按编号倒序、只看未完成任务。需要提前约定页码从 0 还是 1 开始、每页最大数量、允许按哪些字段排序。相同时间或状态的任务还应加 id 作为稳定排序条件，减少翻页时的混乱。

{
  "items": [{"id":3,"content":"喝水","done":false}],
  "page": 1,
  "size": 20,
  "total": 1
}

前端用 items 显示任务，用 total 判断是否还有下一页。数据库查询要把用户参数放进参数绑定；可排序字段应从后端允许的清单中选择。

8. 中文和日期也需要约定

Gson 序列化把对象转成 JSON；浏览器用 JSON.parse 或 response.json() 还原成 JavaScript 数据。传输时 JSON 使用 UTF-8，接收端也按 UTF-8 读取。两端还要约定字段类型，例如 id 是数字、done 是布尔值。

“11月12日星期四”适合展示，却缺少年份。日期字段可以统一成 2026-11-12；具体时刻可以使用 2026-11-12T08:30:00Z，其中 Z 表示 UTC。前端再转换为用户所在时区。别让前端和后端分别猜测时区，也要避免用过大的 JSON 数字承载 JavaScript 无法精确表示的整数编号。

先想一想

只选了“计划在某一天完成”，需要强行写成午夜 UTC 吗？

展开解释

通常不用。计划日期可以直接使用年月日字符串和数据库 DATE。表示一个真正的时间点时，再使用带时区或偏移的时间格式。
