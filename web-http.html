从终端任务清单走向网页

浏览器怎样把一句话交给 Java

你写下“喝水”，点了添加。网页要怎样把这件事说清楚？

假设你托人买东西，只说“帮我办一下”，对方很难知道要做什么。至少要说清楚：去哪里、办什么、带哪些信息。办完之后，对方也要告诉你成了没有。

浏览器请 Java 程序办事，也需要这些信息。HTTP 约定了这份消息怎样组织，让不同人写出来的浏览器和服务器能听懂彼此。

先说要去哪，再说要做什么

你想看任务，浏览器可以向 /api/tasks 这个地址发出“请给我任务列表”的请求。这里的地址由后端提供，浏览器按约定来访问。你可以把它看成任务程序对外接待请求的一个入口。

启动本部分首页的实验程序后，在另一个终端输入：

curl -i http://127.0.0.1:8081/api/tasks

curl 会替我们发送请求，-i 让它把响应头也显示出来。终端里会看到任务 JSON，以及 200 等信息。先把这次交谈拆成两边：

浏览器或 curl 发出：
GET /api/tasks HTTP/1.1
Host: 127.0.0.1:8081

服务器返回：
HTTP/1.1 200 OK
Content-Type: application/json

[{"id":1,"content":"学习 HTTP","done":false}]

GET 说明想读取，/api/tasks 说明读取什么。Host 补充目标主机和端口。回复第一行的 200 表示这次处理成功，后面跟着任务内容。

你看到的这份回复分成两部分：前面说明处理结果和数据格式，后面放真正的数据。中间的空行把两部分隔开。前面的这些说明叫头部，后面的数据叫正文。请求也可以有头部和正文。这里展示的是 HTTP/1.1 的文字形态，后面的协议版本会换一种传输编码，交谈的含义仍然保留。

添加任务，比查询多了一份内容

读取列表时，告诉后端要什么即可。添加任务时，还要告诉它新增什么。我们可以把这段内容写在正文中：

POST /api/tasks HTTP/1.1
Host: todo.example
Content-Type: application/json
Accept: application/json

{"content":"喝水","taskDate":"2026-11-12"}

POST 在这里表示提交创建任务的请求。Content-Type 告诉后端“我这份正文按 JSON 写的”，它才能用相应工具解析。Accept 则告诉对方“我希望收到 JSON”。一个说明自己发的是什么，一个说明希望收什么。

这就是你用过的 Gson 接下来要参与的地方。Java 读到 JSON 文字，转成能使用的数据，检查 content，再交给 TaskDao。数据库处理结束后，Java 把结果转成 JSON，发回浏览器。

上面的创建地址是将来任务接口的约定，观察实验没有实现保存。实验的 /api/echo 可以先把你发来的正文作为文字回传，让你看到中文确实到达了另一边：

curl -i http://127.0.0.1:8081/api/echo   -H 'Content-Type: application/json'   -d '{"content":"喝水","taskDate":"2026-11-12"}'

-H 添加头部，-d 提供正文，并让 curl 默认使用 POST。这个地址只回传文字，不会往数据库添加任务。

两边要把字段名字商量好

如果网页写 title，Java 却找 content，服务器就取不到任务文字。日期也一样：一边发“明天下午”，另一边等着年月日，就无法直接保存。

因此，动手分别写前后端之前，可以先写一份接口约定：哪个地址、什么方法、收哪些字段、返回什么。前端照约定组织消息，后端照约定处理。这就像双方先约好表格每一栏的意思。

我们可以约定：GET /api/tasks 查列表，GET /api/tasks/3 查编号 3，POST /api/tasks 创建任务，DELETE /api/tasks/3 删除编号 3。地址用任务这个名词，动作放在方法里，这样一组接口容易读，也容易猜到相近操作的写法。这是常见的 RESTful 资源命名方式。

如果把一条任务的全部可编辑字段重新提交，可以用 PUT；只改“是否完成”这一部分，可以约定 PATCH。方法名只提供含义，后端仍要实现对应行为。

点了两次按钮，会不会创建两条？

你点添加后，页面迟迟没反应。你再点一次，结果列表出现两条“喝水”。第一次可能已经保存，只是回复在路上丢了；第二次又创建了一条。

这就是为什么“重试”需要考虑操作本身。查询列表多做一次，通常不会多出数据；把指定任务设置成同一份内容，多做一次最终状态也相同；同一条任务删两次，最终仍是不存在。这种重复操作保持相同预期效果的性质叫幂等性。

GET、PUT、DELETE 按语义是幂等的。POST 创建通常不保证这一点。PATCH 要看具体操作：“把 done 设为 true”可以幂等，“把次数加一”就通常不幂等。幂等不要求每次回复都一样，第一次删除成功、第二次回复找不到，也可以符合幂等语义。

后端要避免重复创建时，可以让同一次操作带相同的操作编号，由服务器识别和处理。只禁用网页按钮能改善体验，还需要兼顾网络重试等入口。

回复要让网页知道下一步怎么办

服务器若只回“出错了”，网页没法决定该提示什么。HTTP 用状态码先表达结果的大类，再用正文交代具体原因。

200 常用来表示查询或修改成功；201 表示已创建新资源，通常返回新任务并通过 Location 告诉它的地址；204 表示成功但没有正文，前端此时不需要再解析 JSON。

若正文格式或输入不合适，可以返回 400；需要有效登录凭证是 401；拒绝访问是 403；找不到任务是 404；与当前数据状态冲突可以用 409；正文类型不支持可以用 415；服务器意外出错则可能返回 500。

这些数字服务于操作结果。前端看到 401 可以提示登录，看到内容为空可以请用户补填。后端还可以统一错误正文：

HTTP 状态：400
{
  "code":"TASK_CONTENT_EMPTY",
  "message":"请输入任务内容",
  "requestId":"req-123"
}

code 给程序稳定判断，message 给用户阅读，requestId 方便查服务器日志。详细异常堆栈留在日志，网页只需拿到能指导下一步的信息。

列表长了，就分批拿

如果已有一万条任务，网页一次拿全，等待和显示都不方便。可以约定每次返回 20 条，并允许筛选、排序：

GET /api/tasks?page=1&size=20&sort=id,desc&done=false

这句话可以读成“给我第一页的 20 条未完成任务，编号大的在前面”。双方要约定页码起点、每页上限、可排序字段。排序中加入唯一编号，可以让相同条件的记录有稳定顺序。返回时除了 items，还可以带 page、size、total，方便网页判断是否能翻页。服务端应校验排序字段，并为数据库查询绑定参数。

数据传过去，也要能原样读回来

你原来的“11月12日星期四”适合给人看，却没写年份。接口里的计划日期可以约定成 2026-11-12。具体时刻则需要表达时区，例如 2026-11-12T08:30:00Z 表示 UTC 的这个时间点。网页再转成用户所在地的显示方式。

中文也有同样的“约定”问题：JSON 按 UTF-8 传输，Java 按 UTF-8 读取，就能还原同一段文字。字段类型也要一致，例如 done 使用布尔值；特别大的编号若超出 JavaScript 的整数精度，可以约定使用字符串。

到这里，一条添加任务的请求就完整了：网页按约定写消息，Java 读懂并处理，数据库保存，Java 回传明确的结果，网页再把结果显示出来。
