7. ORM 常见问题，按这几条处理

这页是以后遇到问题时的用法表。当前工程已经处理了 false 更新、软删除与事务边界。

done 改回 false

curl -i -X PATCH http://127.0.0.1:8092/api/tasks/1   -H 'X-API-Key: local-practice-key'   -H 'Content-Type: application/json' -d '{"done":false}'

把 1 换成现存任务编号。预期 done=false。固定写法是请求用 @NotNull Boolean done，Service 在 @Transactional 方法中找受管理实体，再 setDone。Java JPA 不照搬 GORM 的“结构体零值被忽略”规则；这里主要防止把漏填误当成 false。

软删除

本项目 DELETE 设置 deleted=true，Repository 的列表与单条查询都排除 deleted=true。固定使用 findByIdAndDeletedFalse 等方法查询。不要在业务代码直接调用 findById 或 findAll 后忘记过滤。管理员诊断和测试可以有意查看全部行。

预期：DELETE 返回 204，再 GET 返回 404；数据库中仍保留这行。恢复、唯一约束和数据清理需要另外设计，不是多一个字段就全部自动完成。

事务

把需要一起提交的业务放在 Service 的 public 方法上，加 @Transactional；Controller 调用注入的 Service。涉及多个 Repository 操作时仍放在同一个业务方法里。第一轮沿用默认 REQUIRED。

固定避开：同类内部 this 调用事务方法、捕获失败后仍继续返回成功、随意使用 REQUIRES_NEW。默认常对 RuntimeException/Error 回滚，若业务使用受检异常，需要明确 rollbackFor。跨线程也不能假定沿用同一事务。

一次导入多条

curl -i http://127.0.0.1:8092/api/tasks/imports   -H 'X-API-Key: local-practice-key' -H 'Content-Type: application/json'   -d '{"contents":["整理笔记","完成练习"]}'

预期 200，返回两条新任务。当前限制每次最多 100 条，每条非空且最多 200 字符。Service 使用 @Transactional + saveAll。它保证这段方法成功时统一提交，不保证一条 SQL 完成，也不保证已启用 JDBC 插入批处理。

大量导入再考虑批处理配置、分块 flush/clear、内存与重试。IDENTITY 自增会影响插入批处理，不要仅凭 saveAll 名字判断性能。

N+1 查询

当前实体没有关联，不需要提前改。以后增加“任务所属用户”或“任务标签”时，如果列表查询后又逐条补查，先在开发环境观察 SQL 数量，再按页面需要用 EntityGraph、fetch join 或 DTO 投影取齐。EAGER 不保证没有 N+1；集合 fetch join 与分页要专门验证。

常用处理位置：Repository 定义取数方式，Service 决定事务，Controller 返回专门的 TaskView。不要直接把包含复杂关联的实体交给 JSON 转换器。
