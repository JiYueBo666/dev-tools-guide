从终端任务清单走向网页

把整个网站连起来

我们跟着任务走过了请求、缓存和登录，现在看看这些工作分别放在哪里。

用户打开任务网站，先拿到页面。浏览器显示输入框，执行脚本，再向任务接口取数据。后端查询 MySQL，回传 JSON，页面把它显示成清单。

这条路上，页面文件和业务数据有不同的来历。HTML、样式、脚本和图片往往已经放在磁盘上，可以直接发送；任务列表随用户和数据库变化，需要程序现场处理。我们可以让不同工具各自承担适合的工作。

有些内容从文件里直接取

浏览器需要 style.css，服务器找到这份文件就可以返回。这样的文件常被叫作静态资源。JavaScript 文件也可以作为静态资源发送，到了浏览器后再执行，让页面产生交互。

任务列表则要先判断用户身份、查询数据库，再组织响应。它由 Java 程序处理。于是网站可以同时有“提供文件”和“处理业务请求”两条路径。

在门口统一接待，再往后转交

Nginx 可以放在网站入口。浏览器请求页面时，它直接提供静态文件；请求 /api/tasks 时，它把请求转给 Java，等 Java 回复，再把结果交回浏览器。这种替后端接收和转发请求的做法叫反向代理。

浏览器 → Nginx
          ├─ 页面、样式、脚本文件
          └─ /api/... → Java → TaskDao → MySQL

浏览器可以始终面对同一个 todo.example，Java 则在内部端口运行。这样便于集中管理 HTTPS 和静态文件，也能让页面和接口处于同一个来源。最初的本地学习服务可以先自己接收请求，等需要统一网站入口时再引入 Nginx。

下面是一份独立配置示意。路径需要换成真实网页目录，8081 需要对应 Java 服务；这里展示 HTTP，HTTPS 还需配置证书和 TLS：

events {}
http {
    include mime.types;
    server {
        listen 8088;
        server_name localhost;
        root /absolute/path/to/site;
        index index.html;

        location /api/ {
            proxy_pass http://127.0.0.1:8081;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
        location / {
            try_files $uri $uri/ =404;
        }
    }
}

从上往下读，listen 让 Nginx 在 8088 接待请求；root 指定网页目录。/api/ 这一路交给 8081，其余地址尝试寻找文件，找不到返回 404。

proxy_pass 末尾这里没有斜杠，会保留 /api/tasks。若改成 http://127.0.0.1:8081/，匹配的 /api/ 前缀通常会被替换，后端可能收到 /tasks。许多看起来神秘的 404，就来自这类路径变化。

转发头补充原请求的信息，后端只应信任经过自己认可的代理提供的这些头。安装 Nginx 后，可先运行 nginx -t 检查配置语法，再按安装方式加载，并验证路径、文件和端口。

Java 这边，谁负责接待网络消息？

你原来的 Todo 从 main 开始运行，等待 Scanner 输入。要变成网站，必须有工具监听端口、读取 HTTP、把请求交给业务代码。观察实验用了 JDK 自带 HttpServer；Java Web 项目中还常见 Tomcat。

Tomcat 实现 Servlet 规范，管理应用中的请求处理组件。你可以把 Servlet 理解成由容器负责安排的处理组件：请求来了，由容器调用它，组件再调用你的业务代码。框架可以进一步包装路由与参数转换，让日常写法更方便。

一个处理组件，怎样开始和结束工作？

容器创建 Servlet 实例后，调用 init 初始化；请求到来时调用 service，HttpServlet 再把不同方法交给 doGet、doPost 等处理。实例被移除或应用正常关闭等生命周期结束时，容器调用 destroy 清理资源。进程被突然杀掉时，不能依赖一定执行清理。

创建实例 → init → 多次 service → destroy

同一个 Servlet 实例可能同时处理多个请求。若把“当前用户”存进共享实例字段，两个请求就可能互相覆盖。请求自己的数据适合放在局部变量或对应请求上下文中。

连接很多时，谁来处理？

Tomcat 的连接器负责网络入口和协议处理，容器管理应用并分派请求，执行线程运行处理代码。常见安排是工作线程池：请求需要执行业务时，安排线程处理。

连接数量与正在执行的线程数量不必相等。现代连接器可以用非阻塞网络 I/O 管理大量连接。若一个查询很慢，处理请求的线程可能长时间等待；数据库连接池、线程安排和查询速度就会一起影响网站承载能力。具体模型也会随异步、虚拟线程等配置变化。

你已经写好的代码，接下来放在哪一层？

TaskDao 仍然负责访问 MySQL。原来菜单里读取 Scanner、打印结果的那一层，将由 HTTP 请求处理和页面交互接替。可以先只做 GET /api/tasks：后端调用查询，把结果用 Gson 转成 JSON，网页再显示成列表。

等这条路走通，再把输入框接到 POST，把删除按钮接到 DELETE。页面负责让人容易使用，后端负责检查和处理，TaskDao 负责访问数据。前面讨论的所有技术，就这样围绕一次具体操作连了起来。
